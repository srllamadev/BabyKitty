### FINDING-001: Reentrancy in withdraw() due to state update after external call

- **Severity:** HIGH
- **Confidence:** 95%
- **Category:** REENTRANCY
- **Function:** `withdraw(uint256)`

**Description:** The withdraw function performs an external call to the caller before updating the caller's balance. This violates the checks-effects-interactions pattern and allows a malicious contract to re-enter the withdraw function and drain funds.

**Evidence:** Bytecode contains CALL opcode (0xf1) followed by SSTORE that updates the balance mapping. The scanner finding RULE-001 confirms a potential reentrancy pattern with balance checks.

**Impact:** An attacker can drain all Ether from the contract by repeatedly re-entering the withdraw function before their balance is reduced.

**Attack Scenario:** 1. Attacker deploys a malicious contract with a fallback function that calls withdraw again.
2. Attacker deposits 1 Ether into the vulnerable contract.
3. Attacker calls withdraw(1 Ether).
4. The vulnerable contract sends 1 Ether to the attacker's contract via CALL.
5. The attacker's fallback function re-enters withdraw, and since the balance hasn't been updated yet, the check passes again.
6. This repeats until the contract is drained.

**Recommendation:** Update the caller's balance before making the external call (checks-effects-interactions pattern). Alternatively, use a reentrancy guard (mutex) or send funds via transfer() which limits gas to 2300.

**Sources:** llm, rule-engine

### FINDING-002: Authorization bypass via tx.origin in setOwner() and kill()

- **Severity:** MEDIUM
- **Confidence:** 90%
- **Category:** ACCESS_CONTROL
- **Function:** `setOwner(address), kill()`

**Description:** The contract uses tx.origin for authorization in the setOwner and kill functions. This allows a phishing attack where the owner is tricked into calling a malicious contract, which then calls these functions, passing the tx.origin check.

**Evidence:** Bytecode contains ORIGIN opcode (0x45) used in authorization checks. Scanner finding RULE-002 confirms use of tx.origin for authorization.

**Impact:** An attacker can change the contract owner or self-destruct the contract by tricking the legitimate owner into interacting with a malicious contract.

**Attack Scenario:** 1. Attacker deploys a malicious contract that calls setOwner(attacker) on the vulnerable contract.
2. Attacker tricks the owner into calling the malicious contract (e.g., via a phishing link).
3. The malicious contract calls setOwner(attacker).
4. Since tx.origin is the owner, the check passes, and ownership is transferred to the attacker.
5. Attacker can then call kill() to self-destruct the contract and steal funds.

**Recommendation:** Use msg.sender instead of tx.origin for authorization checks.

**Sources:** llm, rule-engine

**Recommendation:** Avoid delegatecall to arbitrary addresses. If necessary, restrict the target address to a whitelist of trusted contracts and ensure proper access control.
