### FINDING-001: Reentrancy in withdraw() due to external call before state update

- **Severity:** HIGH
- **Confidence:** 90%
- **Category:** REENTRANCY
- **Function:** `withdraw`

**Description:** The withdraw function performs an external call to the caller before updating the caller's balance. This violates the checks-effects-interactions pattern and allows a reentrant call to withdraw again before the balance is reduced, draining contract funds.

**Evidence:** Bytecode contains CALL opcode (f1) with balance checks. The function selector 0x2e1a7d4d corresponds to withdraw(uint256). The bytecode shows a balance check (SLOAD of mapping slot 1), then a CALL to msg.sender, followed by an SSTORE to update the balance. The presence of a reentrancy guard (storage slot 0x9b779b... and error 0x3ee5aeb5) indicates awareness, but the guard is only applied to withdraw and not to deposit, and the external call still occurs before state update.

**Impact:** An attacker can re-enter withdraw() and drain all Ether from the contract, causing loss of funds for all depositors.

**Attack Scenario:** 1. Attacker deploys a malicious contract with a fallback function that calls withdraw() again. 2. Attacker calls deposit() to have a balance. 3. Attacker calls withdraw() with a small amount. 4. During the external call, the fallback re-enters withdraw() before the balance is updated. 5. The attacker repeats until the contract is drained.

**Recommendation:** Follow the checks-effects-interactions pattern: update the user's balance before making the external call. Alternatively, use a reentrancy guard (which is partially present) and ensure it is applied to all state-changing functions that make external calls.

**Sources:** llm, rule-engine

### FINDING-005: Unprotected Ether withdrawal by owner

- **Severity:** MEDIUM
- **Confidence:** 80%
- **Category:** ACCESS_CONTROL
- **Function:** `withdrawAll`

**Description:** The function withdrawAll (selector 0xdb2e21bc) allows the owner to withdraw all Ether from the contract. While this may be intended, it poses a risk if the owner is compromised or malicious. The function uses onlyOwner modifier (based on bytecode pattern).

**Evidence:** Bytecode contains function selector 0xdb2e21bc, which corresponds to withdrawAll(). The function checks that the caller is the owner (via a call to a function that checks msg.sender against the owner address stored in slot 0). It then transfers the entire balance to the owner.

**Impact:** If the owner's private key is compromised, an attacker can drain all funds from the contract.

**Attack Scenario:** An attacker who gains access to the owner's private key can call withdrawAll() and steal all Ether.

**Recommendation:** Consider removing the ability for the owner to withdraw all funds, or implement a multi-signature or timelock mechanism to reduce centralization risk.

**Sources:** llm
