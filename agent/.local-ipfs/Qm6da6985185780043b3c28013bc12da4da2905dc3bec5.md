### FINDING-001: Reentrancy in withdraw() due to state update after external call

- **Severity:** HIGH
- **Confidence:** 90%
- **Category:** REENTRANCY

**Description:** The withdraw function performs an external call to transfer Ether to the caller before updating the caller's balance. This violates the checks-effects-interactions pattern and allows a reentrant call to withdraw again before the balance is reduced, draining the contract.

**Evidence:** Bytecode sequence: balance check (SLOAD), then CALL (0xf1) to msg.sender with value, then SSTORE to update balance. The CALL is made before the SSTORE that reduces the balance. This matches the classic reentrancy pattern.

**Impact:** Potential security risk

**Attack Scenario:** An attacker deploys a malicious contract with a fallback function that calls withdraw() again when receiving Ether. The attacker first deposits some Ether, then calls withdraw(). During the Ether transfer, the fallback re-enters withdraw(), and since the balance has not yet been updated, the check passes again. This repeats until the contract's balance is drained.

**Recommendation:** Review and fix

**Sources:** llm

### FINDING-002: tx.origin used for authentication in setOwner() and withdrawAll()

- **Severity:** HIGH
- **Confidence:** 95%
- **Category:** ACCESS_CONTROL

**Description:** The contract uses tx.origin to verify that the caller is the owner in the setOwner and withdrawAll functions. This is vulnerable to phishing attacks where a malicious contract tricks the owner into calling it, and then the malicious contract calls these functions, passing the tx.origin check.

**Evidence:** Bytecode contains ORIGIN (0x32) opcode followed by comparison with the owner address (SLOAD from slot 1) and a revert with 'Not owner' error string. This pattern appears in both setOwner and withdrawAll functions.

**Impact:** Potential security risk

**Attack Scenario:** An attacker deploys a malicious contract that calls setOwner(attacker) or withdrawAll() on the vulnerable contract. The attacker then tricks the legitimate owner into sending a transaction to the malicious contract (e.g., via a phishing site). Since tx.origin is the owner's address, the check passes, and the attacker can change the owner or drain the contract's balance.

**Recommendation:** Review and fix

**Sources:** llm
